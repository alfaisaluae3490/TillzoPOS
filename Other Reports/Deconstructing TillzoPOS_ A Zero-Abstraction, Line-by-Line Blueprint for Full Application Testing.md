# Deconstructing TillzoPOS: A Zero-Abstraction, Line-by-Line Blueprint for Full Application Testing

## Phase I: Comprehensive Codebase Asset Discovery and Micro-Mapping

This initial phase constitutes the foundational discovery and mapping process required to fulfill the mandate of zero-abstraction testing. The objective is to conduct a meticulous, line-by-line scan of the entire TillzoPOS application codebase hosted at `https://github.com/alfaisaluae3490/TillzoPOS`. The output of this phase will be a comprehensive "Micro-Mapping Matrix," an exhaustive inventory of every single UI component, input field, form variable, API endpoint, Google Sheets column, and backend database entity referenced within the project's files. This inventory serves as the absolute prerequisite for generating the subsequent execution scripts for the Hermes AI agent. The methodology employed will combine automated static code analysis with manual, context-aware review to ensure both breadth and depth of coverage, adhering strictly to the directive to include all elements, regardless of their visibility or conditional nature. The discovery process will focus on identifying the exact names, identifiers, locations, and relationships between these disparate assets, creating a detailed blueprint of the application's structure and data flow. This phase directly addresses the user's need to eliminate all generalizations and provide Hermes with a concrete list of every targetable element before any testing logic is applied.

The first step in this discovery process is to establish the complete scope of the application's source code. Based on standard front-end project structures, the primary directory of interest will be the `/src` folder, which conventionally contains all source files [[5](https://medium.com/code-factory-berlin/github-repository-structure-best-practices-248e6effc405), [30](https://github.com/gatsbyjs/gatsby/issues/814), [32](https://stackoverflow.com/questions/40622813/how-do-i-add-the-src-directory-instead-of-the-individual-files)]. This directory will be recursively scanned to locate all relevant file types, including HTML templates, JavaScript (`.js`, `.jsx`), TypeScript (`.ts`, `.tsx`), Vue components (`.vue`), and Angular templates (`.ts`). The scanning script will parse these files to identify all DOM elements and custom React/Vue/Angular components. For instance, it will look for standard HTML tags such as `<button>`, `<input>`, `<textarea>`, `<select>`, `<option>`, `<div>`, and `<span>`. Crucially, it will extract their `id`, `name`, `class`, and `placeholder` attributes, as these serve as unique identifiers for interaction. Custom component names, such as `<AddProductButton />` or `<CategoryDropdown>`, will also be cataloged as they represent higher-level functional modules. This systematic extraction ensures that no interactive or data-bearing UI element is overlooked, fulfilling the requirement to map even "a tiny pixel" by capturing all rendered elements.

Following the identification of UI components, the next task is to discover all associated input fields and form variables. This requires a more focused search within the same set of source files, specifically targeting `<form>` elements and their children. The scanner will meticulously record every `<input>`, `<textarea>`, and `<select>` tag, capturing its `name`, `id`, `type`, `placeholder`, and any associated validation attributes. Beyond simple tags, this phase involves analyzing the application's state management architecture. If the project uses a framework like React with Context, or libraries such as Redux or Zustand, the scanner will look for files related to store or context creation (e.g., `store.ts`, `context.ts`, `reducers.ts`). By tracing how form inputs are bound to state variables (e.g., via `useState` hooks or Redux form bindings), the protocol can establish a direct link between a UI element's identifier (e.g., `productNameInput`) and its underlying data variable (e.g., `productName`). This linkage is fundamental for the subsequent CRUD operations, as it allows Hermes to know exactly which piece of data to manipulate during a test. The use of TypeScript in modern applications provides a significant advantage here; interfaces or types defined for form data can serve as a definitive schema for identifying all expected form variables [[47](https://www.youtube.com/watch?v=wePx13zn0ig), [48](https://www.youtube.com/watch?v=czJp8HQekj8)].

The third pillar of the micro-mapping matrix is the discovery of backend integrations, starting with API endpoints. This involves scanning the server-side source code, typically located within directories like `/src/api`, `/src/routes`, or `/src/controllers`. The scanner will search for patterns that define RESTful routes. In TypeScript-based backends using frameworks like NestJS, it will look for controller classes decorated with route-specific decorators like `@Get()`, `@Post()`, `@Put()`, and `@Delete()` [[52](https://www.notjust.dev/projects/scalable-api-nodejs), [79](https://docs.nestjs.com/techniques/database)]. In Express.js applications, it will identify calls to router methods such as `router.post('/api/endpoint')` or `app.get('/api/endpoint')` [[49](https://github.com/alpacahq/typescript-sdk)]. Each discovered endpoint path, combined with its HTTP method, will be logged as a distinct API endpoint. Furthermore, the scanner will attempt to trace the request handling logic associated with each endpoint. It will look for the corresponding service functions that process the request payload, paying close attention to any data validation logic. The widespread use of libraries like Zod for schema validation in modern TypeScript APIs provides clear markers for defining the expected structure and types of incoming data [[51](https://dev.to/young_gao/building-a-type-safe-rest-api-with-zod-express-and-typescript-from-validation-to-openapi-docs-3agj)]. Capturing this validation schema is critical, as it will later inform the edge-case testing for invalid data types.

Finally, this discovery phase culminates in the complex task of mapping frontend data fields to their corresponding Google Sheets columns. This is a multi-step inference process rather than a direct code-to-sheet lookup. First, the scanner identifies the location of the Google Sheets API credentials, as per the user's confirmation that they reside within the project folder. It will search for configuration files such as `credentials.json`, `.env`, or `config.ts` [[11](https://stackoverflow.com/questions/61262038/can-we-upload-google-sheets-api-credentials-on-github?rq=3), [12](https://community.n8n.io/t/cant-enter-api-credentials-in-google-sheets-credential-window/74312?tl=en), [16](https://craftcms.stackexchange.com/questions/38536/unable-to-use-credentials-json-from-env-file-for-google-cloud-storage)]. The presence of these files confirms the integration is configured and accessible. Next, the scanner identifies the service layer logic that interacts with the Google Sheets API client library (e.g., `googleapis` or `gspread`) [[13](https://github.com/burnash/gspread), [62](https://dev.to/drsimplegraffiti/google-sheets-as-a-database-with-nodejs-and-google-apis-59i5)]. This service function is the bridge between the application's business logic and the external spreadsheet. The scanner will analyze the data being passed into this function. Often, this data is an array of arrays or a list of objects representing rows to be written to the sheet [[25](https://gist.github.com/stefanjudis/868459039f9f02a1aae020b7c6c31a63), [60](https://docs.sheetjs.com/docs/demos/cloud/gsheet)]. By correlating the keys in this data object or the order of values in the arrays with the properties of the TypeScript entities or interfaces defined in the backend models, a tentative mapping can be established. These entities, likely managed by an ORM like TypeORM, define the shape of the data stored in the system [[56](https://tianyaschool.medium.com/typescript-and-typeorm-type-safe-database-operations-c864dd0ac296), [76](https://typeorm.io/)]. For example, if a TypeORM entity has a property `@Column('varchar', { name: 'product_name' }) productName: string;`, it is highly probable that this corresponds to a specific column in the Google Sheet, perhaps one labeled "product_name" in the header row. This inferred mapping, while not perfect, represents the most accurate possible connection given the constraints, forming the basis for the synchronization verification steps in the final protocol. ## Phase II: Line-by-Line CRUD Execution Protocol for Core Modules

With the comprehensive Micro-Mapping Matrix from Phase I as the foundation, this phase focuses on translating the inventory of assets into a strict, step-by-step execution script for the Hermes AI agent. The central directive is to validate the complete Create, Read, Update, and Delete (CRUD) cycle for every single identified module and data field. The instructions must be unambiguous, forcing Hermes to interact with the application precisely as a human user would and then verify the outcome against the predefined expectations derived from the codebase analysis. Each feature will be treated as a discrete unit of work, with its own dedicated protocol block. This phase directly addresses the user's demand for explicit testing of every individual component, ensuring that no part of the application's data lifecycle is left unverified. The protocol will guide Hermes through the entire journey of a piece of data, from its initial entry into the UI, through its persistence in the backend storage (Google Sheets), its retrieval and display, its modification, and finally, its removal.

For each identified module—such as "Product Management," "Inventory Tracking," or "Customer Registration"—the protocol begins by instructing Hermes to navigate to the relevant UI page. Once there, it proceeds to the "Field/Variable Level Test" section. Here, Hermes is given explicit instructions to input specific test data into designated input fields. For example, if the module involves creating a new product, the instruction might be: "In the 'Add New Product' modal, locate the input field with the ID `productNameInput` and enter the text 'Wireless Bluetooth Headphones'. Locate the input field with the ID `productPriceInput` and enter the number '150.99'." This step-by-step guidance prevents Hermes from making assumptions about which fields to fill. The test data used should be varied and meaningful, potentially including alphanumeric strings, special characters, and numbers, to begin probing the system's behavior. This action simulates the initial data capture phase of the CRUD cycle.

The subsequent step, "CREATE & SYNC," is where the data is committed to the system. After Hermes has populated all necessary fields, it is instructed to perform the submit action. This could be clicking a button with a specific `id` or `textContent`, such as "Click the button with the ID `submitProductFormBtn`." Immediately following this action, Hermes must perform a verification check against the primary data source. According to the protocol, this is the Google Sheet. The instruction would be: "Verify that the exact data appears in Google Sheets under the specified columns. Confirm that 'Wireless Bluetooth Headphones' appears in the cell of the newly added row within the column mapped to `productName` (e.g., `Sheet1!B:B`), and that '150.99' appears in the corresponding cell of the column mapped to `productPrice` (e.g., `Sheet1!C:C`). This step validates the 'Create' operation and, critically, confirms the real-time synchronization between the application's frontend and its backend data store. It answers the question: "Does the data we entered get saved correctly?"

Once the data is successfully created and synced, the "READ & SYNC" phase verifies that the data can be retrieved and displayed correctly. The instruction for Hermes would be: "Refresh the browser tab containing the Product List view. Alternatively, navigate away from the current page and return to it." This action simulates a typical user workflow involving a page reload or navigation. Following the refresh, Hermes must inspect the UI to confirm that the data previously submitted is now being rendered accurately. The command would be: "Confirm that the product card or list item for the newly created product displays the correct information. Verify that the element with the ID `productNameDisplay_123` (or similar dynamic ID) contains the text 'Wireless Bluetooth Headphones', and the element with the ID `productPriceDisplay_123` contains the text '$150.99'." This step validates the 'Read' operation of the CRUD cycle and ensures that the data fetching mechanism works as expected, providing a seamless user experience when viewing persisted data.

The "UPDATE & SYNC" phase tests the modification of existing data. The protocol instructs Hermes to find the specific record it created earlier and alter one of its fields. An example command would be: "Locate the product card for 'Wireless Bluetooth Headphones' in the list. Find the inline edit button for the price field (e.g., the button with `aria-label="Edit Price"` next to it) and click it. In the newly appeared input field for the price, change the value from '150.99' to '129.99'. Press the Enter key or click the save icon." After the update action is performed, Hermes must again verify the synchronization with the Google Sheet. The instruction is: "Navigate to the Google Sheet and locate the row corresponding to the product 'Wireless Bluetooth Headphones'. Verify that only the specific cell in the price column (e.g., `Sheet1!C:C`) for that row has been updated to '129.99'. Ensure that no other data in that row has been altered or corrupted." This step is crucial for validating the 'Update' operation and ensuring that partial updates do not cause unintended side effects, maintaining data integrity.

Finally, the "DELETE & SYNC" phase completes the cycle by testing data removal. Hermes is instructed to trigger the delete action for the modified record. The command might be: "In the product card for 'Wireless Bluetooth Headphones', locate and click the button with the ID `deleteProductBtn_123`." A confirmation dialog may appear, requiring an additional step: "If a confirmation dialog appears with the message 'Are you sure you want to delete this product?', click the 'Yes, Delete' button." After the deletion is confirmed, Hermes must perform the ultimate verification: checking the data source for the record's absence. The instruction would be: "Wait a moment for the UI to reflect the change, then verify the state of the Google Sheet. Confirm that the entire row corresponding to the product 'Wireless Bluetooth Headphones' has been completely removed from the sheet." This final step validates the 'Delete' operation and ensures that data is not just hidden from the UI but is permanently erased from the persistent storage, completing the full CRUD lifecycle for that specific data entity.

This structured, repetitive process is applied to every single module and data field identified in the Micro-Mapping Matrix. Whether it's a simple text field or a complex nested object, the same five-step protocol (Field Input, CREATE, READ, UPDATE, DELETE) is followed. This rigorous, methodical approach guarantees that every potential point of failure in the data lifecycle is systematically explored and verified. It transforms the act of testing from a high-level exploration into a low-level, atomic verification process, perfectly aligning with the user's stringent requirements for a production-ready, micro-level protocol.

## Phase III: Deep Edge-Case and System Resilience Audit

Beyond the standard CRUD operations, a truly production-ready protocol must rigorously test the breaking points of the application. This phase, the Deep Edge-Case and System Resilience Audit, provides explicit commands for Hermes to actively probe the system's boundaries and error-handling mechanisms. The user's directive mandates testing for three specific failure modes for every field: empty submission, injection of an invalid data type, and handling of simulated latency or errors. This proactive approach to testing is designed to uncover vulnerabilities that might not be apparent during normal usage, thereby increasing the overall robustness and reliability of the TillzoPOS application. The instructions generated here are not about successful operations but about observing and verifying the system's response to deliberate misuse and adverse conditions. This phase builds upon the Micro-Mapping Matrix by applying stress tests to each identified input field and data-processing module.

The first category of edge-case testing is submission of empty data. For every single input field identified in the codebase, Hermes must be instructed to deliberately leave it blank and attempt to submit the associated form or save the record. The protocol for a field named `productNameInput` would include a specific command: "Navigate to the 'Add New Product' form. Leave the input field with the ID `productNameInput` completely empty. Attempt to submit the form by clicking the button with the ID `submitProductFormBtn`." The subsequent verification step is critical: "Observe the UI for any immediate feedback. Verify that the input field with the ID `productNameInput` is now surrounded by a red border or has an associated error message element (e.g., with class 'error-message') displaying the text 'Product name is required.' Do not proceed until this validation state is confirmed." This tests the frontend's form validation logic. The protocol must be repeated for every required field, and a separate set of instructions must be created for optional fields, instructing Hermes to submit them as empty and verifying that no error messages are displayed and the data is processed as intended. This ensures the application correctly enforces data integrity rules at the point of entry.

The second category involves injecting invalid data types. This test probes the system's defenses against malformed input. The instructions are derived from the data types inferred during the initial mapping phase. If a field is expected to be a number (e.g., `productPriceInput`), Hermes must be commanded to enter non-numeric characters. For a field expecting a date, it must be fed a string. The protocol for `productPriceInput` would be: "In the 'Add New Product' form, locate the input field with the ID `productPriceInput`. Delete any existing value. Enter the text 'invalid-price' into the field." Then, the submit command is issued: "Attempt to submit the form by clicking the button with the ID `submitProductFormBtn`." The verification step focuses on validation feedback: "Confirm that the input field with the ID `productPriceInput` is highlighted with an error state and displays an error message stating 'Product price must be a valid number.'" This test validates that the application does not blindly pass incorrect data types to the backend, which could lead to processing errors or security vulnerabilities. The process is repeated for every field, matching its expected type (string, number, email, URL, etc.) with a corresponding invalid input.

The third and most complex category is testing for timeout and error handling. Simulating network issues is challenging in a scripted environment, but several approaches can be outlined in the protocol. The first approach is to monitor for built-in UI feedback mechanisms. The instruction might be: "Initiate an action that triggers a long-running API call, such as exporting a large dataset. Monitor the browser's developer console for any network requests that take longer than 10 seconds to complete. Observe if a loading spinner or a 'Loading...' message is displayed in the UI during this period." The verification step would be: "After 15 seconds, if the API call has not completed, check the developer console for a 'Request failed: Timeout' error. Confirm that the loading indicator is replaced by a user-friendly error message, such as 'Sorry, we couldn't retrieve the data. Please check your internet connection and try again.'" A second, more advanced approach would involve modifying the test environment itself. The protocol could include commands to toggle a "slow 3G" network condition in the browser's DevTools or to use a proxy to artificially delay responses from the API endpoints. However, since this requires manual setup, the primary instruction would rely on observing existing error states. This ensures the application gracefully handles poor connectivity and provides clear feedback to the user instead of hanging indefinitely.

To make these tests manageable, they should be organized by module. The following table outlines the structure for the audit, demonstrating how these commands would be applied to a hypothetical "Product Creation" module.

This phase moves beyond functional correctness to assess quality attributes like robustness, usability under duress, and fault tolerance. Documenting the results of this audit will provide invaluable insights for developers to harden the application against real-world usage challenges and unexpected inputs.

## Phase IV: Backend Data Synchronization and Integrity Verification

This phase focuses on the critical task of verifying the integrity and accuracy of data synchronization between the TillzoPOS application and its backend data store, which is specified as Google Sheets. While Phase II covered the basic CRUD cycle verification, this phase introduces more sophisticated checks to ensure that the data transfer is not only happening but is also correct, consistent, and reliable. It involves moving beyond simple row-by-row checks to encompass structural validations of the Google Sheet itself, cross-referencing data across different sheets or tabs, and verifying that the data's transformation from the application's internal representation to the flat-file structure of a spreadsheet is handled flawlessly. This deep dive into the backend synchronization mechanism is essential for a production-ready protocol, as data integrity is paramount for any business application.

A primary verification task is to validate the structure of the Google Sheet(s) that the application interacts with. The protocol must instruct Hermes to perform a structural audit of the spreadsheets. This begins with a high-level overview. The command would be: "Open the Google Sheet linked to the TillzoPOS application. Navigate to the sheet tab named 'Products'." The next step is to verify the existence and content of the header row, which defines the schema of the data. The instruction would be: "Inspect the first row of the active sheet ('Products'). Confirm that the column headers match the expected field names as documented in the Micro-Mapping Matrix. Specifically, verify that column B contains 'product_name', column C contains 'product_sku', column D contains 'product_price', and so on." This ensures that the application's understanding of the sheet's layout is correct. Any discrepancy here would indicate a misconfiguration or a mismatch between the application code and the actual sheet structure, leading to silent data corruption.

Beyond verifying headers, this phase includes checks for data consistency and referential integrity, even within the confines of a spreadsheet. For fields that are expected to reference data from another sheet (e.g., a 'Category' dropdown whose options come from a 'Categories' sheet), the protocol must test this relationship. The instructions would be: "In the 'Products' sheet, select a random cell in the 'category_id' column (e.g., cell E5). Note the value in this cell (e.g., 'CAT-007'). Now, switch to the 'Categories' sheet tab. Use the Find function (Ctrl+F) to search for the value 'CAT-007'. Verify that the value exists in at least one cell within the 'Categories' sheet's ID column." This cross-sheet validation ensures that the application is not saving orphaned or invalid foreign keys, maintaining the logical integrity of the data model. This is a powerful check that goes far beyond simple CRUD verification and delves into the relational health of the data.

Another critical aspect of synchronization verification is handling data transformations. When data flows from the application to the spreadsheet, it often undergoes conversion. For example, a boolean `isActive` flag in the application might be stored as 'TRUE' or 'FALSE' in the sheet, or a timestamp might be converted to a formatted date string. The protocol must explicitly test these conversions. For a field like `isActive` (a boolean in the app), the instructions would be: "Using the application's UI, create a new product and set its active status to 'Active' (which corresponds to a TRUE boolean value)." Then, the verification steps would be: "After the record is created and synced, go to the Google Sheet. In the row for the new product, locate the column for the 'is_active' status. Confirm that the cell contains the exact text 'TRUE' (not 'true', 'True', or 1)." This ensures that the serialization/deserialization logic between the application's data models and the spreadsheet's cell values is functioning as intended.

Furthermore, this phase must address bulk operations and their impact on data integrity. The application may have features for importing data from a CSV or performing mass updates. The protocol needs to cover these scenarios. For a bulk import test, the command sequence would be: "Download the sample 'product_import_template.csv' file provided in the application's help section. Open the file in a spreadsheet editor. Add one new row of valid test data. Save the file. In the TillzoPOS UI, navigate to the 'Import Products' section and upload the modified CSV file." The verification would then involve: "After the import process completes, go to the 'Products' sheet in Google Sheets. Verify that the new row of data you added is present and correctly formatted. Also, verify that no duplicate rows were created and that the total number of rows in the sheet has increased by exactly one." This tests the integrity of the import functionality, which is a common source of data duplication or corruption.

Finally, this phase includes a verification of data formatting and localization. Currency, dates, and numbers can be represented differently based on regional settings. The protocol must check that the application correctly formats data for display in the UI and preserves its raw, unformatted value in the backend. The instruction might be: "In the Google Sheet, locate the 'product_price' cell for a specific product (e.g., cell C10). Note the exact formatted value (e.g., '$1,299.99')." Then, the UI check would be: "In the TillzoPOS application, navigate to the product details view for this product. Find the element that displays the price. Confirm that it renders the same formatted value '$1,299.99'." To test the preservation of the raw value, the protocol would add: "Now, click the 'Edit' button for this product. In the price input field, observe the value. It should contain the raw numeric value (e.g., '1299.99'), not the formatted string." This dual-check ensures that data is presented in a user-friendly format in the UI while being stored in a machine-readable format in the backend, preventing calculation errors.

The table below summarizes the key verification tasks for this phase, providing a structured approach to auditing the backend synchronization.

| Verification Task | Protocol Command Summary | Success Criteria |
| :--- | :--- | :--- |
| **Header Schema Validation** | Inspect the first row of the target sheet (e.g., 'Products') to confirm column headers match the expected field names. | All expected columns are present with exact header names as defined in the Micro-Mapping Matrix. |
| **Cross-Sheet Referential Integrity** | Take a value from a foreign key column (e.g., `category_id` in 'Products'), then search for it in the parent sheet ('Categories'). | The value is found exactly once in the parent sheet's ID column. |

By systematically executing these checks, the protocol ensures that the data synchronization layer is not just functional but also robust, accurate, and reliable. It provides a deep level of confidence that the data seen by the user in the TillzoPOS application is a true and consistent reflection of the data stored in the Google Sheets backend.

## Phase V: Finalized Hermes Execution Checklist and Operational Notes

This final phase synthesizes all preceding analyses into a single, monolithic, and strictly formatted checklist. This document is the end-product of the research, designed to be handed directly to the Hermes AI agent for literal, step-by-step execution. Its purpose is to translate the analytical findings of Phases I, II, III, and IV into an unambiguous, imperative script that leaves nothing to interpretation. The structure of this checklist is rigidly defined by the user's initial request, organizing the entire testing protocol around individual features and modules, with explicit instructions for each stage of the CRUD cycle and each type of edge-case test. This concluding section also provides essential operational notes to guide the execution of this massive checklist, addressing practical considerations such as the assumed environment, the handling of conditional UI elements, and the methodology for reporting results.

The checklist itself will be a massive Markdown document, as requested. It will begin with the highest-level modules identified in the Micro-Mapping Matrix, such as "Product Management," "Inventory," "Sales," and "Customers." Under each module, every individual feature, form, or data grid will be listed as a primary heading. For each feature, a standardized block of instructions will follow, mirroring the structure demanded by the user.
